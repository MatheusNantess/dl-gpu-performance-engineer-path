# Learning Log

Running log of the lab. One entry per session, newest first.

The point is not to look productive. It is to make progress *and dead ends* both visible. Failed experiments get logged exactly like successful ones — at kernel level they are usually where the understanding is.

## Format

```markdown
### YYYY-MM-DD — <kernel or topic>

- **Stage:** <lifecycle stage, per KERNEL_WORKFLOW.md, if working on a kernel>
- **Studied:** what was read or worked through
- **Experiment:** what was actually run — link the code, benchmark or profile
- **Result:** what came out of it, with hardware, or "no result / did not work"
- **Next step:** the single next concrete action
```

Rules:

- **Result** is what was observed, not what was expected. If nothing was measured, write "not measured".
- Any number carries the hardware and versions that produced it.
- One **Next step**, concrete enough to start without re-deciding anything.
- Entries for failed optimizations state the hypothesis that turned out to be wrong. That is the useful part.
